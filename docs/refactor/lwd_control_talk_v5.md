## 一、调度结构压缩：把散的收拢（4 分钟）

先讲调度侧。v4 之后有个遗留：边云两个调度器里，同构的扫描写了五遍——判断一个请求是 prefill 相位还是 decode 相位，边侧 flight 打点写一遍、续传判据写一遍、picker 候选过滤写一遍，云侧 decode 收集写一遍、stale 判据写一遍。五处判据靠手抄保持一致。

这轮把它们收进基类三件套：`LwdReqPhase` 枚举、`_lwd_req_phase` 唯一判据、`_lwd_reqs_in_phase` 扫描生成器。五处扫描变成五个调用点，判据从此只有一份。这套手法直接借自九月的参考分支 `prefill_only_refact_scheduler`——那条线虽然整体是 PD 分离架构，但它的结构收敛功夫是通用的。

第二个压缩是边侧 pending 台账。v4 时是两本账：一个 set 记"见过首 token 的请求"，一个 dict 记"seqno 到批内请求列表"，两本账靠两段手抄的扫批循环维持一致。现在的形态是一本账：`dict[seqno, 未到账请求集]`。首 token 到账、请求终结、abort，三条路径共用一个 `_lwd_forget_request`——把请求从它所在的批里消掉，批消空了整条移除。闸门水位就是 len 这本字典。语义逐条对当过，18 个表驱动用例锁着。

顺带修了一个真泄漏：原来 deliver 终结路径从不摘批，正常完结的请求会让它所在的批永远凑不齐"全员到账"，pending 水位只涨不降，闸门最终恒 HOLD。MTP 首步撞 max_tokens 的请求最容易踩中。

【如果被问"为什么不干脆删掉闸门"：单请求 chunk 流下 running 满即天然背压，闸门可以不存在；混排攒批需要背压水位，这是 PD_mix 的功能本体。参考分支没有这两本账，是因为它没有混排。】

## 二、核心机制：可见集 × 钳制（5 分钟）

这部分回答一个检视时被问到的好问题：边侧三个请求组一个 batch 发过来，云侧凭什么保证三条都能排上？

答案是两件事的乘积。**可见性解决"必然被考虑到"，钳制解决"考虑到之后不被拒绝"。**

先看可见性给了什么。混排步把三队列里其余请求全部摘出隐藏，原生调度器的 RUNNING 和 WAITING 循环眼里只剩可见集——decode 驻留加这三条。原生是逐个访问队列成员的，所以每条必然被考虑到一次。但被考虑到不等于被排上，原生有五个拒绝出口：两个守卫会整条跳过，预算会把排程量截短，KV 分配失败会触发抢占把已排的挤掉，新开名额不够直接 break。

五个出口，每个都被一样东西封死。跳过守卫——云侧的 decode 消耗推导逐字复刻了原生那两个守卫的分支，包括 max_tokens 守卫和节拍守卫的零消耗情况，decode 驻留先排、消耗多少算得和原生分毫不差。预算截短——钳制的预算不是"给够"而是"恰好"：decode 精确消耗加三条 chunk 之和，r1 消耗完剩 r2 加 r3，r2 消耗完剩 r3，`min` 永远截不到任何一条。阈值——设成批内最大 chunk，原生截断对每条都是空操作。名额——preflight 先查过，可见集又把名额按隐藏驻留数扣减，break 条件不可能为真。KV——preflight 的预估是保守上界，分配必然成功。

所以完整命题是：可见，必然被访问；五个出口全封，访问后必被全量排上。缺一个都不成立。

【这里是全场技术重心，讲慢点。如果时间紧，后面第三部分可以压到两分钟。】

要如实说的强度边界：这套封死里最脆的是"逐字复刻"——它靠复刻而不是协议。原生升级若改了那两个守卫，decode 消耗推导就和实际脱节，后果不是报错，是末位条目被静默截短。九月的真机事故"604 被排成 608"就是这类发散。旧设计有步后核验兜底，逐请求对排程量和预告量，不等就炸。要不要把这条十行的核验加回来，是今天要请大家拍板的第一件事。

## 三、诊断与执行边界：只出数据，不出适配器（4 分钟）

第三部分讲两个新边界。

诊断收口成 `lwd_control_diag` 子包，一个 `LwdControlDiag` 类管五组东西：两个开关（调用点现读，严格等于字符串 1）、debug 打点转发（lwd_debug 在包内的唯一进口）、spec 接受率观测、SKIP_SAMPLE 旁路载荷、DISABLE_DOWN 直通判定。边界规则一句话：**诊断只出判定与数据，不出执行适配器。** 开关是布尔，载荷是行集，future 一律不给。

为什么 future 不给？中间走过弯路。第一版把伪输出和直通 future 也搬进了诊断包，检视时被指出来：伪 ModelRunnerOutput 的主用户是功能路径——每个无输出批都要拿它的空实例兜底 None，把它放进诊断包，等于让功能执行契约依赖诊断模块，恰好是反向的糅合。现在的形态：诊断回答"这个批要不要直通、直通内容是什么"，边引擎的 executor 代理拿行集自己包装 future。

executor 代理本身也统一了。`LwdEdgeExecutorProxy` 一个类管三项契约：None 换空占位、诊断直通短路、属性透传。stub 和两个 future 全部封成内部类，模块层不外泄——这条边界有测试锚着，谁再把内部类拎出去，测试当场红。

收个尾。这轮的原则回头看就一句：结构跟着查询走——相位判据收成一份，两本账并成一本；边界跟着数据走——诊断出数据不出适配器，代理出契约不出判定。加上 38 个用例里三张守卫网（外部 import 面、依赖方向、诊断纯度），结构回退会被测试拦住。

## 问答预案

- **Q：钳制这么精确，为什么不干脆自己排，绕过原生？**
  A：绕过原生就要自己维护准入、KV、抢占、占位记账全套，v4 之前的四场事故就是那套平行实现的代价。钳制复用原生，出问题时对账对象是同一个原生实现。

- **Q：decode 消耗推导逐字复刻的维护成本？**
  A：它引用的原生片段有行号注释锚定（scheduler.py:381-416 一带），原生改动会在升级 diff 里显式出现。这也是恢复步后核验的理由：复刻漂移从静默错排变成当场报错。

- **Q：诊断开关为什么坚持调用点现读？**
  A：排障场景需要在进程不重启的情况下动态开旁路；构造期定格会把这个能力关掉。代价是热路径上一次 getenv，两个字符串比较。

- **Q：与参考分支的关系？**
  A：结构手法（相位生成器、对账回收、函数拆分纪律）已吸收；其组批模型（单请求 chunk 流 + 纯相位）与 PD_mix 互斥，未采纳；其 wire 演进（eos_discard、token_offsets、mrope 行序）属协议变更，单独立项。
