## 开场（1 分钟）

各位好，今天讲 lwd_control 控制面的这轮重构。三个数字先摆出来：包内代码从 3497 行降到 2490 行，净减 29%；引擎步进覆写从三个降到零；测试从零到 29 个用例。

这次重构的目标里没有减代码这一项。目标只有一个问题：vLLM 原生已经有的机制，我们为什么维护着一套平行的？09-22 那天四场真机事故，超批两倍 cap、604 被排成 608、prefill 静默串行 280 步，全部出在我们自己那套平行实现的接缝上。所以这轮的原则就一句话：原生有的用原生，自己写的每一行，都要有原生给不了的理由。

【停顿。这一句是全场纲领，后面每个设计决定都回扣它。】

## 一、先讲清楚问题（3 分钟）

LWD prefill_only 的架构：边侧进程持有真实 prompt，只做 embedding；云侧进程拿占位缓冲跑 decode；两边靠 ZMQ 控制面和 UP/DOWN 数据面张量通道协作。

重构前的状态，我用三个"平行实现"概括。

第一个平行，步进。原生引擎有批队列机制 step_with_batch_queue，但边侧引擎不用它，自己覆写了三个方法，自建一个 deque 批队列，手工编排"收割、派发、消费"三段。

第二个平行，生命周期。原生调度器管请求从入队到终结，但边侧请求在 embedding 完结时被 finish 出调度器，之后由三本手工台账，一个 dict 两个 set——代管，原生看不见这些请求，我们自己记账。

第三个平行，输出钩子。云侧把 c2e 通告的发布挂在 core.py 的模型输出钩子链上，为此改了上游文件，每步还带调试日志。

平行的代价是接缝。两个系统各对一半账，对不上就是 bug。四场事故都是这么来的。

【如果听众问四场事故细节，指向设计文档 §8 风险清单和 09-22 的 git 记录，不展开。】

## 二、云侧：动了手脚的原生调度（4 分钟）

现在讲怎么改的。先讲云侧，因为它最能体现"用原生"是什么意思。

云侧调度器每步要决定：这一步把哪些请求、各排多少 token 放进一个批。它的特殊之处在于，批里 prefill 部分的答案边侧已经替它决定好了。为什么？两条硬约束：

第一，张量在预告后面飞。边侧发布预告的同一拍就发出 embedding 张量，云侧 worker 已经按序号预挂了接收。云侧排多少，张量就是多少，排错一行，张力注错窗口，静默错算。

第二，一步只产一个调度输出。没有"先让原生填一部分、回读、再填"的窗口。

所以云侧的方案是：每步先过四道门，这条预告的请求落地了吗？张量收完了吗？预算名额 KV 装得下吗？全过，就做一次隔离调用。

隔离调用是什么？【指屏幕上的示意图】我们想让原生代码自己算出批内容，但它不能看见全部请求——waiting 里住着占位请求，原生会自作主张放行它们。于是把它没点名的请求藏起来，把它读的预算改成"decode 精确消耗加预告总量"，把它读的截断阈值改成"批内最大块"，然后调 super().schedule()。原生代码以为自己在自由发挥，其实世界是造好的，它算出来的每个数字，恰好等于边侧预告的数字。

这里有一个最精细的细节：decode 精确消耗必须逐字复刻原生的推导公式，包括两个守卫分支。为什么？这个数马上要当预算用，多算 4 个 token 的余量，末位截断块就被超排，604 排成 608 那场事故就是这么来的。

结果：core.py 里的 LWD 残留只剩 10 行引擎选择。c2e 的发布也不再需要钩子链，调度器收割时只记账到一个列表，引擎在原生的 post_step 钩子里统一发出去。

【如果被问"为什么不裸调原生"：那两条硬约束就是答案，展开见设计文档 §2。】

## 三、边侧：零覆写（4 分钟）

边侧更彻底：step、step_with_batch_queue、has_work，三个覆写全部删掉，直接用父类的。LWD 的契约靠三个构造期适配满足。

第一，批队列深度设为 4，size 和上限同步重建。

第二，把 is_pooling_model 置 True。这个属性全仓只有原生采样分支一个消费点，置掉它，原生就不会给边侧的批补发一轮多余的采样。

第三，executor 代理。这里有个真实的坑：底层 executor 被重写后，正常完成默认返回 None，而原生把 None 判成执行失败直接抛异常。代理坐在引擎和 executor 的边界上，把"正常完成的 None"换成空占位，异常照样穿透，不吞真失败。诊断旁路也收在代理里：不发张量的批，代理直接返回一个携带旁路 token 的已完成 future，走和正常批完全一样的原生收割路径。

删掉覆写后有个必须解决的问题：原生批队列的隐含契约是"调 schedule 必有真批"，空批会以 None 结果炸掉收割。我们把 has_requests 覆写成一个谓词——有没有可派发的批，闸门关着且没在飞的请求时，谓词为假，引擎直接睡眠。空批从产生机制上消失了，它不是被拦住，是不存在。

然后是生命周期迁移，这是最大的一步：嵌入完结的请求不再 finish 出调度器，留在 running 里转 decode 相位等云结果。从此原生的请求账本就是唯一事实源，在途数一处读数，迟到结果按账本判定，终结由云端完成码映射回原生 finish。三本台账删掉两本，剩下一本服务 pending 闸门，它管的是云侧消费水位，跟请求住哪没关系。

## 四、证据（2 分钟）

改了这么多，怎么证明没改坏？

picker 组批算术：从基线逐字取出原算法做对照实现，随机两万组用例对拍，prompt 长度覆盖到 65536，预算从 0 到 16384，零分歧。另有 17 个手推边界用例常驻测试。

接口守卫：云侧不 import 边侧有扫描和测试双重断言；core.py 零 LWD 钩子有文本断言；已删模块有存在性断言。

行为对账：每条路径在流程差异文档里逐项对照，标注了全部有意偏差。最大的一条是防御核验按拍板全删，chunk 划分漂移从当场报错变成静默错算，回归防线移到 CI 和联调，这要大家知情。

诚实交代：过程中我自己引入过三次静默伤，都是机械替换没带命中断言，孤儿装饰器、残留方法调用、缩进未命中。三次全修了，教训写进了台账，机械改动必须带断言。

## 五、收尾（1 分钟）

三个数字背后的三个转变：步进从自建到原生、生命周期从台账到原生账本、输出从钩子链到原生钩子。平行的系统删掉了，接缝消失了，事故的温床也就没有了。

留给检视的三个动作：一，真机冒烟按风险清单跑，长序列加多模态混发，抽日志比对排程量与预告量；二，RFC issue 建立并关联 MR；三，三个规范拍板项，注释语言、日志前缀、诊断开关时机，需要定论。

## 问答预案（备注，不读出）

Q: 防御核验删了，划分漂移怎么办？
A: 短期靠冒烟清单第一条兜底；中期把它做成 CI 检查，对比排程量与预告量的日志断言；要恢复单项核验，git 历史里逐段都在。

Q: pending 闸门那本账为什么不一起删？
A: 它跟踪的是云侧消费水位，与请求住哪无关。删它需要协议加一个字段，c2e 携带已消费 seqno，是独立小改，列为后续候选。

Q: 为什么不直接抄参考分支？
A: 抄了手法，没抄形态。参考分支能用纯原生是因为它连生命周期模型一起换了，请求留 running 加占位欠条，换完连修三场。我们等原生步进、自定义收割、wire 带完成码三个前提齐了才迁生命周期，风险结构完全不同。

Q: 边侧深度为什么硬编码 4？
A: 拍板保持与重构前同值；配大配小是后续实验项。

Q: 两仓怎么配合？
A: vllm-ascend 本轮零改动，跨仓只读确认过，分支同名对齐即可联调。
